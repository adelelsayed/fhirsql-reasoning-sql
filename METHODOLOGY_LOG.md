## Floating-point non-determinism in AVG() aggregates -- discovery, fix, and full-pipeline regeneration (2026-08-12)

**Discovery.** Checking the first real heldout eval results, `gen_exact_match` (98.4%) was higher than `gen_exec_match` (90.9%) on the familiar arm for both SFT seeds available at the time -- logically impossible if predicted SQL text truly matches gold, since identical SQL executed twice against the same database must return identical results. Tested directly: 80 of the familiar arm's `AVG(...)`-based gold queries, run 5 times each with byte-identical SQL, no changes -- 61/80 (76%) returned a different floating-point value on at least one run, differences appearing at the 10th-15th decimal place (e.g. `6.324210914763363` vs `6.324210914763366`). Root cause: DuckDB's parallel query execution reorders floating-point summation non-associatively across threads -- a known property of parallel aggregation engines, not a bug in the schema or data.

**Why this matters beyond the eval numbers.** `_exec_rows`'s exact-equality comparison is the shared correctness check used in three places: `evaluate_generation` (both notebooks' accuracy metrics), `compute_reward` (RL's training-time reward), and the last cell's SFT-vs-RL efficiency comparison. Any `AVG(valueQuantity)`-based completion that was actually correct could have been scored as wrong purely from this jitter -- and within a DAPO group of `group_size` completions, this could inject *spurious* reward variance, causing Dynamic Sampling to keep and train on groups where the apparent "difference" between samples was measurement noise, not a real quality difference. This means the RL training that had already completed for seeds 42 and 43 carried this noise in its reward signal the whole time.

**Full-pipeline audit, not just the familiar arm.** Repeated-execution stability tested systematically across every gold-SQL category, both databases:

| Source | Statements | Unstable | Rate |
|---|---|---|---|
| Train main + operational | 2,487 | 241 | 9.7% |
| Train quality_kpi + regulatory | 220 | 0 | 0.0% |
| Heldout familiar | 2,268 | 236 | 10.4% |
| Heldout unseen | 295 | 0 | 0.0% |

All instability traced to exactly 5 archetype IDs, every one doing `AVG()` directly on the raw floating-point `observation.valueQuantity` column: `t1_avg_observation_value`, `t2_observation_high_values`, `t2_observation_by_year`, `t3_condition_avg_observation`, `t4_observation_trend_yearly_delta`. Five *other* `AVG()`-using archetypes (`t3_avg_procedures_per_patient_with_condition`, `t3_condition_encounter_count`, `t3_procedure_avg_patient_age`, `t4_time_from_condition_to_medication`, operational's `avg_length_of_stay`) showed zero instability, and this is structural, not luck: they all average an *integer* expression (a per-patient count, or a `DATE_DIFF` result), and integer summation is exact regardless of thread order -- only floating-point summation is order-sensitive. Grepped the full `scripts/` directory for `SUM(`, `STDDEV`, `VARIANCE`, `PERCENTILE` to confirm no other float-aggregate risk exists anywhere.

**Fix, two layers (same principle as the earlier ORDER BY tiebreak fix -- fix at the source, then harden the comparison layer as defense-in-depth):**
1. **SQL-level (`scripts/archetypes.py`):** wrapped all 5 affected `AVG(...)` expressions in `ROUND(..., 4)`, including inside the `t4_observation_trend_yearly_delta` CTE (so the downstream `LAG()`-based year-over-year delta is computed from an already-stable value). This alone reduced instability from ~76-95% to near-zero: re-verified 3 of the 5 archetypes at exactly 0% instability, the remaining 2 (both `GROUP BY <year>`, higher-cardinality result sets) down to ~19%.
2. **Comparison-level (`_exec_rows`, both notebooks):** the remaining cases are genuine rounding-*boundary* flips (e.g. `4.1260` vs `4.1261`), which no amount of added SQL-level decimal precision can eliminate -- a boundary problem exists at any finite precision, just becomes rarer. Added a `_round_val` helper that rounds any `float` value to 2 decimals (100x margin over the observed ~0.0001 residual) before both sorting and comparing, applied uniformly rather than only to the 5 known-affected archetypes so any other float-producing SQL is covered too. Verified this closes the gap: train's residual dropped from 14/282 to 1/282 (0.35%, an inherent boundary-flip in a *derived* field -- `yoy_delta` is a subtraction of two already-rounded averages, so it can hit the identical boundary phenomenon one level down; not chased further since going coarser trades away real precision without ever reaching exactly zero). Heldout familiar: 15/282 raw down to 0/282 with the comparison fix.

**Full regeneration required** (gold SQL text itself changed for the 5 archetypes -- not just a comparison-layer patch): re-ran `generate_gold_sql.py` (train main: 2,288 verified, unchanged from the prior baseline) -> `generate_all_backtranslations.py` (9,152 rows, unchanged) -> re-merged `sft_final.jsonl` (11,844 rows, unchanged -- confirms the fix didn't change *which* queries succeed, only made the affected ones deterministic). Same for heldout familiar: `generate_heldout_gold.py familiar` (2,268 verified) -> `generate_heldout_backtranslations.py familiar` (9,072 rows) -> re-merged `heldout_benchmark_familiar.jsonl` (10,088 rows) -- all counts identical to the prior baseline. Heldout unseen arm was **not** regenerated -- it has zero `AVG()`-based archetypes (scoped to tier-1/2 condition/procedure/medication_request only), confirmed unaffected by the audit above, so there was nothing to fix there.

**Consequence: all previously-computed results are now stale.** The heldout eval numbers already downloaded (frozen, SFT seed 42, SFT seed 43 -- both arms) were computed against the *old* gold SQL and must be discarded, not just re-cached. The RL training already completed for seeds 42/43 trained against the old (jittery-reward) gold SQL too. The fix is made permanent (both notebooks, both databases) and the *entire* pipeline -- SFT, then RL, then heldout eval -- is re-run from scratch rather than attempting to patch or reuse any prior run's artifacts.

**Backported to `sft_train.ipynb` while making this pass (2026-08-12):** `gen_efficiency_speedup` (median gold-time/pred-time among exec-correct rows, same cache-fair warm-up+randomized-order timing methodology as `rl_train.ipynb`'s reward and metric) did not previously exist in SFT's `evaluate_generation` -- it was added to `rl_train.ipynb` after `sft_train.ipynb` was frozen mid-training, which is why the three-way ablation table's frozen/SFT-only rows showed `nan` for this metric. Backported now that SFT is no longer actively training, so a fresh SFT run will produce a real value here instead of `nan`. While in the function, also batched it the same way `rl_train.ipynb`'s `evaluate_generation` was batched (multiple prompts per `generate()` call instead of one at a time) -- was harmless at `eval_gen_sample_size=60` but no reason to keep paying per-call overhead 60 times over once the pattern already existed to copy.

**Fixed batch sizes, probes removed (2026-08-12).** Both notebooks' training-step batch-size probes were re-run every session for an answer that had stopped changing across repeated real runs -- confirmed empirically stable at `micro_batch_size`/`train_micro_batch_size` = 14 in both notebooks, so both probe cells were removed and the value set directly in `CFG`, saving real GPU time every run. `rl_train.ipynb`'s separate `rollout_prompts_per_batch` probe (a different concern -- generation batching, not training-step batching) was kept, since that value has a different memory profile (no backward pass, but KV-cache scales with batch x sequence length) and wasn't reported as having converged to a fixed answer.

## Reversed course: full heldout eval restored, with a lenient unseen-arm correctness metric (2026-08-16)

Third design pass on the same underlying problem in one session -- worth recording the sequence, not just the final state, since each step was a real reconsideration, not a mistake being corrected: (1) discovered the code-recall confound, (2) halted heldout eval and built a standalone table-selection + familiar-only-efficiency diagnostic as a narrower replacement, (3) reconsidered -- decided the standalone diagnostic was throwing away everything else the full heldout eval already computed (perplexity, abstention precision/recall, the generalization-gap framing) just to avoid one bad metric, when the better fix is to *replace what "correct" means for the unseen arm specifically*, not abandon the eval that computes everything else.

**Implemented:** a new `gen_structure_match` metric in `evaluate_generation`, computed alongside (not replacing) `gen_exact_match`/`gen_exec_match`. `_normalize_structure(sql)` strips the literal `code`/`system` VALUES out of a WHERE clause via regex (`code = '...'` -> `code = '<CODE>'`, same for `system`), collapses whitespace, and two SQL strings are considered structure-matching if they're identical after that normalization -- same table, same aggregation/grouping/join shape, same everything except which specific clinical code was used. A prediction that queries the right table with the right query shape but a hallucinated/wrong code now counts as `gen_structure_match=True` even though it still (correctly) scores `gen_exact_match=False` and almost certainly `gen_exec_match=False`. Deliberately eval-only -- `compute_reward` (RL training) is untouched, since "is this acceptable to report as correct" and "is this acceptable to reward during training" are different questions, kept separate deliberately.

`CFG['run_heldout_eval']` reset to `True` (full 3-way x 2-arm eval restored). Interpretation, not enforced by any code: **familiar arm** still leans on `gen_exact_match`/`gen_exec_match` as primary, and is the only arm `gen_efficiency_speedup` is meaningful for (unseen's rarity leaves too few exec-correct rows for a stable estimate). **Unseen arm** should be read primarily via `gen_structure_match` going forward -- a reading note to this effect prints at the end of the heldout eval report. The standalone table-selection/efficiency diagnostic built in the previous pass is left in place (still useful, still independent, still safe to run without re-enabling the full eval) rather than deleted, since it doesn't conflict with this restoration.

## Diagnostic revised: per-arm table-selection + familiar-arm efficiency, unified sample (2026-08-16)

The first version of the table-selection diagnostic (above) had two real problems, surfaced by direct questioning rather than caught proactively: (1) it sampled from `HELDOUT_ROWS['familiar'] + HELDOUT_ROWS['unseen']` combined, which is ~82% familiar-weighted by population size (10,088 vs. 2,196 rows) and reported one combined number -- silently capable of hiding a real unseen-arm-specific degradation; (2) its 300-row sample size was picked as "fast and cheap," not from any actual power reasoning, and would have been even thinner once correctly split by arm. Fixed: table-selection is now computed **separately per arm** and both numbers are reported, and both diagnostics reuse `HELDOUT_GEN_SAMPLE` (750/arm, already built unconditionally regardless of `CFG['run_heldout_eval']`) instead of a separate smaller ad hoc sample.

Also added to the same pass: a **familiar-arm SQL efficiency check** (frozen vs. SFT vs. SFT+RL, per seed), reusing `gen_efficiency_speedup` from `evaluate_generation` directly rather than writing a new bespoke metric -- median gold-time/pred-time among exec-correct rows, same cache-fair methodology used everywhere else this metric appears. This is a heldout-data answer to "did RL make correct SQL faster," distinct from the last cell's `compare_sft_rl_efficiency`, which only compares SFT-vs-RL (no frozen) on the **in-corpus** test split (`train.duckdb`, same population as training) -- worth keeping the two straight, since with `CFG['run_heldout_eval']=False` the last cell is the only efficiency comparison that still runs on its own; this diagnostic is what restores a heldout-based one without re-enabling the full (halted) heldout eval. Unseen arm is excluded from the efficiency check specifically -- those concepts are rare enough (1-3 patients each) that too few rows would ever be exec-correct to produce a stable speedup estimate.

## Code-lookup-via-SQL redesign, motivation (2026-08-16 -- since implemented, see DESIGN.md)

**Full design document:** [DESIGN.md](DESIGN.md) -- the summary below is the original reasoning that led to it; the design document has the concrete technical design (DuckDB CTE-based lookup, the `valuesets` table built from existing `concept_bank.csv` profiles, archetype redesign, and a full scoped work list).

Investigating the unseen arm's weak SFT numbers (`gen_exact_match=0.027`, `gen_exec_match=0.207` vs. familiar's 0.984/0.984) surfaced a real design flaw, not just a data-scarcity issue: **every gold SQL template filters by exact literal `code`, never by `display`** (e.g. `WHERE code = 'C7B.1'`, never `WHERE display ILIKE '%merkel%'`). Since the model only ever sees the question and the schema -- no concept dictionary, no code-lookup mechanism, no RAG -- getting the unseen arm's SQL right requires the model to already know, from its own parametric knowledge, that "secondary Merkel cell carcinoma" maps to `C7B.1` under ICD-10. That's testing medical-coding recall, not FHIR-SQL-translation skill, and it's a self-inflicted conflation: the training data taught the model the *fragile* strategy (memorize codes) when a *robust* one (look up the code via the schema itself) was always available, using data already in the tables (`display` sits right next to `code` in every resource).

**The real fix, deferred rather than implemented in this pass** (given the amount of full-retrain churn already absorbed): don't hardcode literal codes into gold SQL at all. Instead, gold SQL for concept-parameterized archetypes should be a **two-step pattern the model learns to reproduce**: (1) resolve the concept mentioned in the question to its code via a `SELECT DISTINCT code, system FROM <table> WHERE display ILIKE '%<term>%'`-style lookup (or a subquery/CTE doing the same), then (2) use that resolved code in the actual COUNT/LIST/aggregate query. This requires no RAG, no external tool-call infrastructure, no prompt-format change -- it's ordinary SQL against columns that already exist in every core table. It tests the actual target skill (can the model navigate FHIR-shaped data to answer a question) without conflating it with "has this exact code been memorized," and it would make the familiar/unseen concept-arm distinction far more meaningful (a model taught to look codes up should show a *much* smaller familiar-vs-unseen gap than one taught to recall them, and how much smaller becomes a real, reportable number).

**Scope:** archetype templates in `scripts/archetypes.py` (and `operational_archetypes.py`/`quality_kpi_archetypes.py` wherever they parameterize by a searchable concept) need a lookup-then-answer SQL pattern instead of direct literal substitution; back-translation questions don't need to change (the NL question already just names the concept in prose). Full data regeneration and a full SFT+RL retrain are required. See `DESIGN.md` for the design that was actually built from this reasoning.

## Heldout failure-diagnostic logging (2026-08-16)

The unseen arm's SFT-seed42 numbers (`gen_exact_match=0.027`, `gen_exec_match=0.207`, vs. familiar's 0.984/0.984) prompted a question this log can't answer from aggregate metrics alone: is the model hallucinating a *familiar* (trained-on) code instead of the genuinely novel one the question asks about, producing malformed SQL, or something else? `evaluate_generation` (both notebooks share the pattern, only wired into `rl_train.ipynb` so far) now accepts an optional `failure_log_path` -- when set, every failing row is appended (not buffered to the end, so an interrupted run keeps whatever it already processed) as one JSON line: `{archetype_id, tier, question, gold_sql, pred_sql, failure_type, exec_error}`, using the same four-way `failure_type` taxonomy as the RL reward tiers (`wrong_result` / `non_executing` / `false_abstention` / `missed_abstention`) so failure logs and training reward penalties line up directly. `evaluate_state_on_heldout` takes an optional `label` (`'frozen'`, `'sft_seed<N>'`, `'rl_seed<N>'`) and writes to `HELDOUT_EVAL_DIR/failures/{label}_{arm}.jsonl` when given. Off by default (`None`) since `evaluate_generation` also runs on every RL training-step eval, which shouldn't grow a failure log every few steps.

Seed 42's frozen/SFT-only legs are already cached (computed before this change) and won't re-run, so no failure logs exist for them -- accepted deliberately rather than forcing a recompute just to backfill logs for a leg that already produced valid aggregate numbers. Seeds 43/44 and any not-yet-computed RL legs will produce real failure logs on their next run.

**Also this pass:** reconciled a manually-tuned Colab session copy (`rl_train (1).ipynb`, downloaded 2026-08-16) against the canonical file -- only real difference (beyond the canonical copy having picked up flash-attention/torch.compile/RunPod support the Colab session predates) was two deliberately-tightened values, `early_stopping_patience=2` and `save_every_n_steps=2` (both default to 5) -- preserved rather than overwritten with the canonical defaults.

## Flash Attention / Triton / RunPod infrastructure (2026-08-12)

**Flash Attention 2**, both notebooks: `FHIRSQLLLM._load_base_model()` now picks `attn_implementation` via `_pick_attn_implementation()` rather than leaving it unspecified -- tries `flash_attention_2` only if the `flash_attn` package is importable AND the GPU is Ampere+ (compute capability >= 8.0, FA2's hard requirement), otherwise falls back to `sdpa` (PyTorch's own fused attention, still efficient, just without FA2's specific memory/speed profile). A best-effort install cell (`pip install flash-attn --no-build-isolation`, skipped if already importable) was added after the existing `!pip install` cells -- the build can take 10-20 minutes and isn't guaranteed to succeed on every environment, so this degrades gracefully rather than blocking the notebook.

**`torch.compile` (Triton/TorchInductor), both notebooks:** added as opt-in only (`CFG['use_torch_compile']`, default `False`), wired into `SFTTrainer.__init__`/`RLTrainer.__init__` right after the model moves to `DEVICE`, via a `_maybe_compile()` helper. Deliberately not on by default: both notebooks pad every batch to that batch's own longest sequence rather than a fixed length (SFT: dynamic per-step padding; RL: rollout completions of varying length) -- a full static compile would recompile on every new shape, which can cost more wall-clock than it saves. When enabled, uses `dynamic=True` specifically to compile a shape-flexible graph instead of specializing per-shape, trading some peak speedup for robustness to that variability. Still flagged as experimental in the code comment -- bitsandbytes' custom autograd ops for 4-bit quantization are a known source of `torch.compile` graph breaks that can silently reduce or eliminate the expected speedup, so this should be verified on a handful of real steps (timing before/after) rather than assumed to help.

**RunPod compatibility, both notebooks:** added as a third environment alongside Colab and local-Windows, detected via `RUNPOD_POD_ID` (set in every RunPod container). Designed around a **persistent network volume** (confirmed available, mounted at `/workspace`) rather than ephemeral local disk -- this matters architecturally: unlike Colab's Drive FUSE mount (which has real async sync lag, see the 2026-08-07 checkpoint-loss incident), writes to a persistent RunPod volume are durable plain local-disk writes, so the existing "write checkpoints straight to `ROOT`" code needed *zero* changes -- it already generalizes correctly once `ROOT` points at the volume. The only new logic is a one-time `rclone copy <remote> ROOT` pull of the read-only inputs (model weights, schema, DBs, training data) when a fresh volume doesn't have them yet, gated behind `ON_RUNPOD` and skipped entirely on Colab/local. rclone itself is installed on demand if missing; if no Drive remote is configured, the cell raises with clear setup instructions rather than failing confusingly later -- Google OAuth can't be completed non-interactively from inside a notebook cell, so this is necessarily a one-time manual step per pod (`rclone config`, or copying an already-authorized `rclone.conf`). An optional `push_to_drive_backup()` function (not called automatically) is available for off-volume backup/convenience, since it isn't required for durability given the persistent-volume assumption.

## Evaluation objective

The central empirical claim this pipeline is built to support: a three-way comparison -- frozen base model, SFT-tuned (DoRA), and SFT+RL-tuned (DoRA+DAPO) -- evaluated on `heldout.duckdb`, the population disjoint from every patient used to build any training data (see "Synthetic patient corpus" below). This is what the ablation/comparison machinery in `sft_train.ipynb`/`rl_train.ipynb` exists to produce; it is not the same thing as the in-corpus `test` split those same notebooks also report, which is a training-time/development diagnostic (`dev` participated in checkpoint selection, and even `test` is drawn from the same patient population every training row came from) rather than evidence of generalization.

The comparison is meant to answer four things directly: (1) SFT's impact over the frozen base, on both accuracy metrics (exact-match, execution-match, abstention precision/recall) and perplexity/token-accuracy; (2) RL's incremental impact over SFT-only, on the same accuracy metrics; (3) how much execution-efficiency DAPO's reward term actually bought (`gen_efficiency_speedup`, measured only over exec-correct rows), and whether that efficiency gain cost any accuracy -- i.e., whether SFT+RL's accuracy metrics are ever worse than SFT-only's, not merely whether the reward was structurally correctness-gated at training time; (4) whether training helps the model generalize to medical concepts it never saw during SFT/RL at all, not just to unfamiliar patients -- see "Heldout benchmark design" immediately below. Point (3)'s gating (see "Reinforcement learning setup" below) is a design safeguard against reward hacking, not itself evidence the safeguard worked in practice -- the trio comparison on heldout data is the empirical check.

**Heldout benchmark design: two concept arms, not one.** Rather than a single heldout benchmark, the design uses two, built from disjoint concept pools within `heldout.duckdb`, so the frozen/SFT/SFT+RL trio can be evaluated on each separately:
- **Familiar-concepts arm**: archetypes parameterized only by concepts that also appear in train's `selected_concepts.csv` (the 382 concepts used to build all training data). All 382 exist in heldout's concept bank (verified by direct set intersection on `(table_name, code)`), spanning all 8 core-table categories the training archetypes use. This arm isolates *population* generalization: same concepts the model was trained on, entirely unfamiliar patients.
- **Unseen-concepts arm**: archetypes parameterized only by the 87 concepts that exist in heldout's concept bank but never appear anywhere in train's full concept bank (2,595 concepts) -- not merely excluded from the 382 selected, but absent from Synthea's train-population output entirely. This arm isolates *concept* generalization: genuinely novel medical codes the model's SFT/RL data could not have contained under any selection policy. Verified directly (not assumed): these 87 concentrate in only 3 tables -- condition (58), procedure (23), medication_request (6) -- Synthea simply generated no novel codes in observation/encounter/immunization/allergy/diagnostic_report for the heldout population, so this arm cannot have full archetype-category parity with the familiar-concepts arm. That asymmetry is a real property of the data, not a shortcut taken in building the benchmark, and should be reported as such.

The generalization-gap metric this produces: for each of frozen/SFT/SFT+RL, compute accuracy metrics on both arms; the drop from familiar-arm to unseen-arm is the population-independent "concept generalization gap." Whether SFT/RL narrows that gap (learns transferable schema/SQL structure) or widens it (overfits to the specific 382 trained concepts) is itself a reportable empirical result, not just a robustness check.

As of this writing, both arms of the heldout benchmark are built and execution-verified (`data/training/heldout_benchmark_familiar.jsonl`, 10,088 rows; `heldout_benchmark_unseen.jsonl`, 2,196 rows), and `rl_train.ipynb` has a dedicated section that evaluates frozen/SFT-only/SFT+RL on both arms and reports the generalization-gap table. What's still missing is not the benchmark or the wiring, but the checkpoints to run it against: every cell in that section skips until SFT produces at least one seed's `best/` checkpoint. The frozen/SFT-only/SFT+RL comparisons currently computed on the in-corpus `test` split remain a useful development-time sanity check, but are not a substitute for the heldout numbers once they exist.

## Schema

Two-layer design: the underlying DuckDB database holds every FHIR resource type Synthea exported (full fidelity, nothing discarded), but the schema shown to any model in a prompt is a deliberately curated subset -- schema DDL is injected into every prompt across every baseline configuration and every training/RL example, so token cost compounds across hundreds of eval configurations, and tables outside the clinical-decision-support domain (billing/claims, document management, audit trail) add hallucination surface area without adding signal.

**11 benchmark-facing tables:** patient, condition, observation, medication_request, encounter, procedure, immunization, allergy, careplan, diagnostic_report, imaging_study.

Column names follow FHIR element names as closely as SQL allows, so a model's existing FHIR knowledge transfers directly to this schema rather than requiring it to learn an arbitrary naming convention:
- Primary key `id` (every FHIR resource's own `id` element); foreign keys `patient_id`/`encounter_id` (a SQL join-key convention resolving FHIR reference elements to a flat key).
- Coding triple `code`/`system`/`display` (FHIR `Coding.code`/`.system`/`.display`); where a resource's own field isn't literally called "code" (Encounter.type, Encounter.class, Immunization.vaccineCode, CarePlan.category), the triple is prefixed with that field's real name instead (`type_code`/`type_system`/`type_display`, `class_code`, `vaccineCode`/`vaccineCode_system`/`vaccineCode_display`, `category_code`/`category_system`/`category_display`).
- Status/descriptive fields use exact camelCase FHIR names (`clinicalStatus`, `verificationStatus`, `intent`, `criticality`).
- Dates use exact FHIR element names (`birthDate`, `deceasedDateTime`, `onsetDateTime`, `abatementDateTime`, `recordedDate`, `effectiveDateTime`, `authoredOn`, `performedDateTime`, `occurrenceDateTime`); `Period.start`/`.end` as `period_start`/`period_end`.
- `value[x]` polymorphism (Observation) flattened into `valueQuantity`, `unit` (`Quantity.unit`), `valueCodeableConcept` (+ `valueCodeableConcept_system`), `valueString` -- keeping both a value's code and its code system lets code-system confusion (SNOMED vs. ICD-10 vs. LOINC) surface as an observable failure mode rather than being hidden.
- Provider-reference columns named for their source field: `requester_npi`/`requester_name` (`MedicationRequest.requester`), `participant_npi`/`participant_name` (`Encounter.participant`) -- both are FHIR *conditional references* by NPI identifier rather than direct resource-ID references, extracted accordingly.
- `race`/`ethnicity` on patient, parsed from US-Core extension arrays (nested `extension[url=...].extension[url=text].valueString` structures, not a flat field).

All ID/reference fields extracted via regex on the reference string; all dates via a non-strict cast so partial/malformed FHIR date-times degrade to NULL rather than failing the whole load (date precision issues are exactly the kind of thing a failure-mode taxonomy over model outputs wants to be able to observe, not something that should silently abort ETL).

Encounter always has exactly one participant, typed "primary performer" -- Synthea does not model distinct admitting/attending/consulting roles, so those remain structurally indistinguishable. `Procedure.performer` is never populated by this Synthea version, so procedure-level physician attribution is unavailable regardless of schema design.

## Data profiling and concept selection

Per-table row counts, column fill rates, and a concept bank (every distinct `(table, code, system)` triple with row count and distinct-patient coverage) computed directly from the flattened data. Concept bank: **2,595 distinct concepts** in the train population, **1,248 at >=50-patient coverage**.

Concept selection for the training-data factory excludes near-universal administrative/SDOH-demographic codes with no differential clinical signal (e.g. a "medication review due" boilerplate code present in 100% of patients, employment-status/education-level findings, dental-referral administrative procedures), and applies a 90%-of-population coverage ceiling to condition/procedure/encounter specifically (a near-universal code doesn't discriminate for "which patients have X"-shaped questions), while leaving observation/diagnostic_report unrestricted (ubiquitous vitals like heart rate are legitimate subjects for "compute stats of X"-shaped questions regardless of how common they are). Selection spreads across the coverage range per table rather than taking the top-N by patient count, so the concept set includes both common and rare concepts.

**382 concepts selected**, distributed: condition 90, observation 70, medication_request 60, procedure 45, allergy 21, immunization 21, encounter 45, diagnostic_report 30.

## Training-data generation

Gold SQL is generated programmatically from parameterized query templates ("archetypes") instantiated against selected concepts, then execution-verified against the live database: every candidate query is run, and kept only if it executes without error **and** returns at least one row (a query returning zero rows is trivially "correct" for a broken query that also returns zero rows, which would let reward-based training exploit the gap). Gold SQL is built as literal SQL text with values embedded directly, matching what a model must actually produce, and the exact same text that is verified is the text that ships as training data.

**Clinical archetypes:** 40 templates across four difficulty tiers -- single-table/single-filter; single-table/multi-filter/grouping; 2-3-table joins with aggregation; and longitudinal/temporal patterns (window functions, top-N-per-group, cohort-then-outcome). Each archetype is parameterized by one concept; a handful of join/temporal archetypes that inherently need a second clinical anchor (e.g. "patients on medication X who also have condition Y") use a fixed companion concept (hypertension, lisinopril, colonoscopy, anemia) rather than a second free parameter, keeping the concept x archetype factory combinatorially simple. **2,288 of 2,346 instantiations verified (97.5%)**, all rejections attributable to genuinely empty result sets (e.g. a rare condition that never co-occurs with the fixed companion concept within the studied population), zero execution errors.

**Regulatory-reporting archetypes**, modeled on the general pattern of periodic hospital regulatory reporting common to public-health and pharmaceutical-oversight regimes rather than invented from nothing (illustrative of the category of reporting obligation, not a citation of any single jurisdiction's statute): notifiable-communicable-disease surveillance (HIV, Hepatitis B/C, COVID-19, all confirmed present in the corpus at low-but-nonzero patient counts, included as a deliberate exception to the general >=50-patient concept floor since low prevalence is precisely why these are mandated reportables) at monthly reporting cadence; narcotic medication consumption at quarterly cadence and controlled-non-narcotic consumption at monthly cadence. **31/31 verified.**

**Operational archetypes:** physician-level attribution (top prescribers for a medication, top diagnosing physicians for a condition, encounter volume by physician and month), inpatient bed occupancy (point-in-time census via admission/discharge-interval overlap, monthly admission counts, average length of stay, 30-day readmission rate via a lead/lag comparison of consecutive inpatient stays per patient). **199/199 verified.**

**Demographics, quality-indicator, and imaging archetypes:** patient counts by race/ethnicity/state and condition prevalence by race/ethnicity; mortality review and fall-risk-screening volume by month, in the spirit of a standard hospital quality-KPI program; imaging-study volume by month and by modality. **189/189 verified.**

**Unanswerable/abstention data:** questions referencing data genuinely absent from the 11-table schema, with the gold target being a fixed abstention marker rather than SQL -- this trains a model to decline rather than hallucinate a plausible-looking query, and lets abstention be rewarded/penalized as its own category (a correct refusal and a confident wrong answer are not the same failure mode and should not be scored as if they were). Categories include: physician role disambiguation (admitting vs. attending, not distinguishable in this schema), patient nationality, future/scheduled appointments, department/ward assignment, facility address, full care-team composition, audit/provenance history, radiology ordering department, practitioner specialty, billing amounts and claim status, clinical-note free text, medication-administration events as distinct from the order, pharmacy/supply inventory, implanted devices, and insurance payer. Each category was checked against the frozen schema before use to confirm the referenced field is structurally absent (not merely a concept that wasn't selected) -- a false "unanswerable" label would train refusal on genuinely answerable questions, a worse failure mode than the one this data targets. Concept- and instance-parameterized categories reuse the selected-concepts pool or a curated instance list (device types, insurance payers, department names, supply items), since the missing-data category is independent of which concept is named. **1,016 rows generated.**

## Back-translation (natural-language question generation)

Each verified gold-SQL artifact is paired with several natural-language paraphrases across a roster of eleven hospital roles (physician, nurse, pharmacist, admission/registration clerk, outpatient clerk, emergency department manager, ICU manager, finance reviewer, hospital CEO, population health analyst, infection control officer), mapped per archetype rather than assigned uniformly at random -- a hospital CEO asks trend/aggregate questions, a nurse asks patient-level care questions, a finance reviewer asks volume questions; a tier-1 single-patient lookup is never phrased as a CEO-level question.

Paraphrase quality is checked with an automated filter verifying that the question still references the concept the underlying SQL actually filters on (catching a paraphrase that silently drops a filter present in the source query), implemented as a soft flag for human review rather than automatic deletion, since valid synonyms and abbreviations (e.g. "H&P" for "history and physical note") would otherwise false-positive under literal keyword matching.

## Known limitations of the data source

These are structural properties of the synthetic data generator, not artifacts of schema design choices, confirmed by direct inspection rather than assumed:

- **No future or scheduled encounters.** The generator produces completed lived history up to a fixed reference date only; there is no way to query upcoming appointments.
- **No pharmacy/inventory data.** No resource type in this data model represents stock levels or supply movements.
- **No claims adjudication variance.** Every claim and claim-response record in the underlying data has an identical "submitted and paid" status; there is no rejected, denied, or resubmitted state anywhere in the corpus, so claims-outcome questions have no signal to query regardless of schema.
- **No department/service-line concept.** Nothing in the data model represents hospital departments or wards, so department-level attribution (e.g. which department ordered an imaging study) is unanswerable independent of what else is exposed in the schema.
- **No nationality/country-of-origin field.** The generator produces only US-based synthetic patients with US state/city addresses.
- **Physician role is undifferentiated.** Exactly one generic "primary performer" is recorded per encounter; admitting, attending, and consulting are not separate roles in this data.

## Storage and infrastructure

The flattened corpus is stored as an embedded, single-file database (DuckDB) rather than a hosted database server: reproducibility (no server/credentials to keep alive or drift), zero network-hop latency for the reward-computation loop used in reinforcement-learning training (any hosted database, however fast, adds latency that a purely in-process embedded file avoids), license-clean and free, and consistent with standard tooling in NL-to-SQL research generally. Each table is also exported to Parquet for a compact, portable copy suitable for syncing to cloud storage for GPU-based training; cloud-mounted filesystems have real read-latency overhead for the kind of many-small-reads access pattern a reward loop performs, so the recommended workflow copies the file to local disk at the start of a training session rather than querying the mounted copy directly.

## Supervised fine-tuning setup

Base model: `Qwen/Qwen2.5-Coder-14B-Instruct`, loaded via bitsandbytes 4-bit (NF4, double quantization, bfloat16 compute dtype) rather than a pre-quantized static checkpoint (GPTQ/AWQ/GGUF) -- QLoRA training attaches LoRA adapters on top of a bitsandbytes-quantized base, which requires starting from the original full-precision weights and quantizing at load time, not a separately pre-quantized artifact built for inference-only serving.

**LoRA target modules:** all seven linear projections in every decoder layer -- attention (`q_proj`, `k_proj`, `v_proj`, `o_proj`) and MLP (`gate_proj`, `up_proj`, `down_proj`). Restricting adaptation to attention-only projections (the original LoRA paper's minimal recommendation) leaves a measurable gap to full fine-tuning performance; the QLoRA paper (Dettmers et al., 2023) found that extending LoRA to all linear layers, attention and MLP alike, closes that gap and is the now-standard QLoRA recipe. `embed_tokens` and `lm_head` are excluded -- no new vocabulary is introduced (the abstention marker tokenizes from existing tokens), and both are large relative to the rest of the network (152,064 x 5,120), so adapting them risks destabilizing general-purpose token representations for no corresponding benefit on this task. Existing attention bias terms (`q_proj`/`k_proj`/`v_proj` carry `bias=True` in this checkpoint) are left frozen (`LoraConfig(bias="none")`), consistent with standard QLoRA practice and keeping trainable-parameter count minimal given the dataset size (11,844 rows).

**Adapter variant:** DoRA (Weight-Decomposed Low-Rank Adaptation, Liu et al., 2024) rather than plain LoRA -- DoRA decomposes each targeted weight matrix into a magnitude vector and a directional component, applying the low-rank update only to direction while letting magnitude train separately, which the DoRA paper shows tracks full fine-tuning's learning behavior more closely than plain LoRA at the same rank. Enabled via `use_dora=True` on the same `LoraConfig` (target modules, rank, and alpha unchanged) -- the module-targeting and rank rationale above apply identically.

**Prompt format:** system message = fixed instructions (SQL-only output, no markdown fencing, abstain with the literal string `UNANSWERABLE` when the schema genuinely can't answer the question) followed by the schema DDL; user message = the row's natural-language question; assistant message = the row's gold SQL or `UNANSWERABLE`. The DDL shown to the model is `schema/schema.sql` with its human-facing changelog header stripped (everything before the first `CREATE TABLE`) -- the model needs the table definitions and their inline column comments (several of which encode real signal, e.g. the note that `encounter` only ever has one participant, which is exactly why physician-role-disambiguation questions are unanswerable), not the revision history. Loss is computed only over the assistant span (`labels` masked to `-100` everywhere else), located via the token-level prefix produced by the chat template's own generation-prompt marker -- verified empirically to be an exact prefix of the full-conversation tokenization before being relied on for masking, rather than assumed.

Because the full schema DDL is repeated in every prompt, sequence length is dominated by the schema itself (1,176 tokens under the Qwen2.5-Coder tokenizer) rather than by the question or answer. Measured directly against all 11,844 rows with the real tokenizer: p50=1,379, p95=1,449, p99=1,498, max=1,518 tokens. `max_seq_len` is set to 2,048 accordingly; a truncation-time assertion in the training `Dataset` fails loudly if any example's prompt alone would exceed `max_seq_len` and leave no room for the answer, rather than silently masking every label and producing an uninformative zero-signal loss.

**Train/dev/test split for SFT:** grouped by underlying SQL instance (`archetype_id` + `concept_display` + gold SQL), not by row, so that back-translation paraphrases of the same query never span two sides -- an ungrouped random split would let dev/test "accuracy" partly reflect memorized phrasing rather than generalization. A fixed three-way split (8% dev / 8% test / 84% train, by instance) is shared across all training seeds; seeds vary only weight initialization and batch order. `dev` is used during training for per-epoch checkpoint selection; `test` is held out entirely until training finishes and evaluated exactly once per seed, on that seed's best-by-dev-loss checkpoint -- reporting SFT impact on `dev` alone would be mildly optimistic, since the checkpoint was chosen specifically to minimize loss on that data. No nested cross-validation: unlike a small fixed clinical cohort where every subject's assignment affects the generalization estimate, this dataset is a deterministic archetype x concept factory, and the study's actual out-of-corpus generalization claim is evaluated against the separate, disjoint held-out benchmark -- `dev` and `test` here exist for checkpoint-selection and leakage-safe in-corpus reporting during SFT development, not as the study's central evidence.

**Frozen-base-model baseline:** every metric below is also computed once against the unmodified base model, using PEFT's `disable_adapter()` context manager to strip the DoRA adapter's effect from the same already-loaded model rather than loading a second copy -- since disabling the adapter always yields pure base-model behavior regardless of how much training the adapter has seen, this is safe to compute at any point and is cached after the first computation rather than repeated per seed (deterministic under greedy decoding, so recomputation would just repeat the same answer). The generation-based spot-check below draws from one fixed subsample of the dev set, reused for the baseline and for every epoch of every seed -- an unfixed subsample would let apparent SFT improvement partly reflect which rows happened to be drawn rather than the model itself.

**Final held-out evaluation:** the frozen-base-model comparison is repeated on `test` (not just `dev`), computed once per run and cached separately from the dev-based baseline. For each seed, its best-by-dev-loss checkpoint is loaded onto the same resident base model (PEFT's `load_adapter`/`set_adapter`/`delete_adapter`, not a second model load) and scored on `test` once training completes. This test-based comparison, not the dev-based per-epoch one, is the number reported as "SFT impact" -- the dev-based numbers are a training-time diagnostic only, since dev participated in checkpoint selection.

**Training-time evaluation:** two tiers. A fast pass (loss + next-token accuracy over the assistant span) runs every epoch and drives best-checkpoint selection. A slower periodic pass greedy-decodes a subsample and scores exact SQL-text match, DuckDB execution-result match (order-insensitive, against the same `train.duckdb` every gold statement was already execution-verified against), and abstention precision/recall -- computed separately from SQL-correctness metrics, consistent with treating a correct refusal and a confident wrong query as distinct failure modes (see "Training-data generation" above).

**Actual run parameters (2026-08-05 restart), confirmed against the real session rather than assumed from the notebook default:** Colab, G4 GPU (96GB RAM) -- corrects an earlier assumption in this log that the run was on an A100 40GB, which was never confirmed against the actual Colab session. `micro_batch_size=12`, found via the empirical batch-size probe on this actual hardware rather than guessed. Seed 42 ran for 3 epochs; its 3rd epoch showed no useful improvement over the 2nd (per-epoch dev metrics), so seeds 43/44 were capped at 2 epochs rather than spending compute on a non-useful epoch. This means seed 42's best-by-dev-loss checkpoint could in principle come from either epoch 2 or 3 (checkpoint selection already handles this correctly since it compares dev loss, not epoch number), while seeds 43/44 only ever had 2 epochs to select from -- worth keeping in mind if seed 42 is ever compared to 43/44 on training compute spent, though not on final checkpoint quality (selection is by dev loss regardless).

## Reinforcement learning setup

RL continues each SFT seed's best-by-dev-loss checkpoint with DAPO (Decoupled Clip and Dynamic sAmpling Policy Optimization; Yu et al., 2025), a GRPO-family (Shao et al., 2024) policy-gradient method: no learned value/critic network, advantage is the within-group reward z-score across several completions sampled for the same prompt. Three of DAPO's four techniques are used -- Clip-Higher (asymmetric PPO clip bounds, `eps_low=0.20`/`eps_high=0.28`, the paper's own reported values, which give low-probability tokens more room to grow than high-probability tokens get to shrink, counteracting entropy collapse), Dynamic Sampling (prompt-groups where every sampled completion received the same reward are dropped and replaced, since a zero-reward-variance group's advantage is exactly zero and contributes no gradient), and token-level loss normalization (by total response-token count across the batch, not by sequence count then averaged, avoiding length bias). Overlong Reward Shaping, DAPO's fourth technique, is not used -- it exists to discourage runaway-length generation in DAPO's original long chain-of-thought math domain (responses running to thousands of tokens); SQL responses here are capped at a few hundred tokens and typically only a few dozen, so that failure mode doesn't apply.

**Reward:** correctness-gated, reusing the exact success criteria already established for SFT's `gen_exact_match`/`gen_abstention_*` metrics -- 1.0 if the gold is `UNANSWERABLE` and the model correctly abstains, or if the gold is SQL and the model's SQL executes with the same result set (order-insensitive) as gold; a tiered penalty otherwise (see below). No partial credit above 1.0 for a wrong answer of any kind, and no hand-tuned shaping beyond the efficiency term and the wrong-answer tiering below -- Dynamic Sampling exists specifically to make sparse binary verifiable rewards sample-efficient, so shaping the base reward itself would work against the method's own design if it weren't done carefully (see next paragraph for why the tiering doesn't count as that kind of shaping).

**Tiered wrong-answer penalty (2026-08-08):** originally all four wrong-answer cases (non-executing SQL, executing-but-wrong-result SQL, false abstention on an answerable question, missed abstention/hallucinated SQL on an unanswerable question) collapsed to a flat `0.0`. This interacted badly with Dynamic Sampling: a group of `group_size=4` completions that failed in four *different* ways still had zero reward variance (all scored identically at 0.0) and got dropped exactly like a uniformly-correct group, discarding real rollout compute and (more importantly) discarding gradient signal Dynamic Sampling's advantage computation could otherwise have extracted from the relative differences between failure types. Replaced with four tunable `CFG` constants ranked worst-to-least-bad by how much the failure reflects genuine SQL/schema understanding: `reward_wrong_result=0.0` (executes, wrong result -- unchanged, the mildest failure, since it demonstrates valid SQL/schema use, just wrong logic), `reward_non_executing=-0.2` (doesn't execute at all), `reward_false_abstention=-0.1` (gave up on an answerable question), `reward_missed_abstention=-0.3` (confidently hallucinated an answer to a question with no correct SQL answer at all -- ranked worst specifically because this is a clinical-data context, where false confidence is judged more harmful than an honest failure to answer or a broken query). This ranking is a value judgment specific to this project's priorities, not an objective fact, and is documented as such rather than presented as self-evidently correct. The existing reward-hacking safeguard (a wrong answer can never outscore a correct one) is unaffected and still holds by construction -- all four tiers are negative or zero, strictly below the >=1.0 floor for any correct answer -- and is now asserted immediately after `CFG` is built (`assert max(...) < 1.0`) rather than only claimed in a comment.

**Efficiency term, and the risk it was added to avoid creating:** a small bonus, up to `efficiency_bonus_max` (0.1), is added on top of a correct answer if the query's wall-clock execution time beats the gold query's own -- intended to teach a preference for well-targeted SQL among otherwise-equally-correct answers, once correctness alone stopped being the only thing decided. The obvious risk of adding *any* speed signal to a correctness reward is that the policy learns to trade correctness for speed (a trivially fast wrong query outscoring a slower correct one). This is closed structurally, not by tuning a weight: the bonus only ever applies inside the branch that already confirmed the result set matches gold exactly, and the 0.0 branch for a wrong answer has no path to add it -- there is no bonus value large enough to make a wrong answer beat a correct one, because a wrong answer's score is fixed at 0.0 regardless of how the bonus is computed.

**Risk: cache-order bias in the timing measurement itself.** Timing two queries back-to-back on the same DuckDB connection is not a fair comparison by default -- whichever query executes second inherits buffer-pool pages the first query already pulled in, so it looks artificially fast independent of how well it was actually written. Combatted with two changes: (1) both queries are run once, untimed, before any timing starts (a warm-up pass that the correctness check needs to run anyway, so it costs nothing extra), so both enter the timed comparison in an equally warm state; (2) the order of the two *timed* executions is additionally randomized per call, so neither query systematically inherits residual state from that second pass either. This roughly doubles DuckDB execution count per correct-answer reward computation (4 executes instead of 2) -- an accepted cost for removing a systematic, directional bias rather than just adding noise. Timings are also floored at `efficiency_min_timing_ms` (0.5ms) before the speedup ratio is computed, so measurement noise on sub-millisecond queries can't produce a large spurious bonus from timing jitter alone.

**Risk: rewarding this database's physical layout rather than genuinely well-written SQL.** `train.duckdb`/`heldout.duckdb` were built via plain `CREATE TABLE ... AS SELECT` (see Schema/Storage sections) with no indexes of any kind, despite `schema.sql`'s logical DDL declaring `id` as a primary key -- that constraint was never physically enforced. Without any index, a timing difference between two queries mostly reflects how much of one specific unindexed file's row groups got scanned, which is only loosely related to whether the SQL itself was well-formed, and risks teaching the model to exploit this file's incidental layout rather than a transferable notion of efficient SQL. DuckDB's own indexing model bounds how far this can be fixed, though: its secondary (ART) index is only used by the optimizer for point lookups and highly selective filters (roughly <0.1% of rows) -- confirmed before deciding what to index, not assumed -- and is not used to accelerate joins at all, where DuckDB relies on hash joins built at execution time regardless of any index. So indexing `patient_id`/`encounter_id` (used almost exclusively as join keys across the archetype SQL) would add build cost with no plan-level benefit; indexing the coding-triple columns (`code`/`system` and table-specific equivalents) is the part expected to matter, and only for the archetypes that target genuinely rare concepts (the regulatory/notifiable-disease archetypes' low-prevalence codes are the clearest case) rather than common ones, where a full columnar scan is already close to optimal regardless of indexing. Applied to both `train.duckdb` and `heldout.duckdb` together, not train alone, so the efficiency signal means the same thing wherever it's later measured -- indexing only the RL training database would create a train/eval mismatch this study would have to revisit anyway. Indexes change execution speed only, never query results, but re-verification (re-running every previously-verified gold SQL statement and confirming identical results) was still treated as required before trusting the change, consistent with this project's standing rule of re-checking rather than assuming after any change to a frozen data artifact.

Twelve indexes created (`condition.code`, `observation.code`, `medication_request.code`, `encounter.class_code`, `encounter.type_code`, `procedure.code`, `immunization.vaccineCode`, `allergy.code`, `careplan.category_code`, `diagnostic_report.code`, `imaging_study.procedureCode`, `imaging_study.modality`), identically on both databases. `heldout.duckdb` re-verification (24 structural smoke-test queries, since no gold SQL has ever been generated against this population) matched exactly, before vs. after. `train.duckdb` re-verification against all 2,707 unique gold SQL statements surfaced two problems, neither of which was indexing being wrong:

- **A latent bug in `_exec_rows`** (the result-set comparison helper shared by SFT's `evaluate_generation` and RL's `compute_reward`): `sorted()` on raw result tuples throws `'<' not supported between float and NoneType` the instant a result column mixes `NULL` and non-`NULL` values across rows (e.g. `AVG()` returning `NULL` for one group, a real number for another). Both callers catch exceptions and score the query as 0.0/no-match on any error, so this wasn't crashing loudly -- it was silently mis-scoring otherwise-correct queries as wrong whenever their result happened to contain a mix of NULL and non-NULL in a compared position. Unrelated to indexing; re-verifying against real query output is simply the first time this comparison path had been exercised. Fixed by sorting on `(value is None, value)` per column instead of the raw value, which keeps `None` orderable without ever comparing it to a real number.
- **Seven archetype templates generate non-deterministic gold SQL**: `t4_first_diagnosis_age_per_patient`, `t4_top5_patients_by_medication_count`, `t4_top5_patients_by_condition_recurrence`, `doctor_top5_by_encounter_type`, `doctor_top5_prescribers`, `doctor_top5_by_condition_diagnosed` (all `ORDER BY <count> DESC LIMIT 5` with no tiebreak column), and `t4_observation_first_vs_last` (`ROW_NUMBER() OVER (PARTITION BY patient_id ORDER BY effectiveDateTime)`, also no tiebreak). When multiple rows tie on the ranking criterion, which ones land inside the `LIMIT`/`rn=1` boundary depends on physical scan order, which indexing (or any other plan-affecting change -- a DuckDB version bump, a different thread count, different hardware) can alter. Confirmed directly, not assumed: every sampled mismatch returned identical values, just different patient/physician IDs at the tied boundary. This predates the indexing work and is independent of it -- indexing only acted as the plan-perturbing change that exposed a fragility that was already there. Affected 254 of the 2,707 unique gold statements (~9.4%).

**Fixed at the source**, not patched around: each of the 7 templates got an explicit deterministic tiebreak column added to its `ORDER BY` (the grouped/ranked column itself -- `patient_id`, `participant_name`, `requester_name`, or `id` for the window-function case) in `archetypes.py`/`operational_archetypes.py`, so which rows land at a tied `LIMIT`/`rn=1` boundary no longer depends on physical scan order at all. This meant regenerating the affected slice of training data rather than leaving the existing text in place: re-ran gold-SQL generation + back-translation for the `main` and `operational` categories (the two categories these 7 templates belong to; `regulatory`/`quality_kpi`/`unanswerable` were untouched since none of their templates changed), re-merged all five category files into `sft_final.jsonl`, and re-verified the complete result -- same totals as before the fix in every category (2,288/2,346 main, 199/199 operational, 11,844 total rows, 2,707 unique answerable statements, 0 execution errors, 0 empty results), confirming the fix changed *what* gets returned for ties without changing *which* instantiations succeed. Additionally re-ran all 481 statements from the 7 fixed archetypes twice each and confirmed identical results both times (0/481 non-deterministic) -- not just "still executes," genuinely reproducible now. This directly required restarting the in-progress SFT run, since the training data it was using changed underneath it -- an accepted cost, not an oversight.

**Consequence of the efficiency term for Dynamic Sampling:** a group where every sampled completion is correct previously had exactly zero reward variance (all 1.0) and was dropped as uninformative. With the efficiency term, such a group can now carry a small, meaningful variance and get kept -- which is the intended effect, not a side effect to guard against: it lets the model learn to prefer the more efficient of several equally-correct queries instead of that comparison being discarded as noise.

**Rollout:** one prompt at a time, but its `group_size` sampled completions are generated together in a single batched `model.generate(num_return_sequences=group_size, ...)` call, not sequentially. Each sampled completion is trimmed to its own first EOS token before use, so no sample carries trailing padding into the loss. `max_new_tokens_rollout=256` was checked directly against the real tokenizer rather than assumed sufficient: gold SQL answer length across 1,500-row samples of `sft_final.jsonl` and both heldout arms tops out at 193 tokens (mean ~75, p99 ~188) -- not a single gold statement anywhere in the corpus exceeds 256, since every archetype is a single `SELECT` (COUNT/AVG/GROUP BY over 1-3 tables), never a multi-statement script. 256 leaves ~33% headroom above the observed worst case for a generated completion to run longer or more verbosely than any gold answer.

**Batching (2026-08-06):** two places originally ran one forward pass per sample -- `sample_group`'s old-logprob computation (one forward call per completion in a `group_size`-sized group) and `RLTrainer._train_step`'s training forward+backward loop (one call per kept sample, up to `rollout_groups_per_batch x group_size` per step) -- the same fixed-per-call-overhead bottleneck already diagnosed and fixed for SFT's `micro_batch_size=1`. Both are now batched: `sample_group`'s old-logprob pass is one right-padded batched call across the whole group (inference-only, so safe to pad unconditionally, no probe needed -- `group_size=4` is small and fixed); `_train_step` is chunked into `CFG['train_micro_batch_size']`-sized micro-batches via a shared `_dapo_backward_chunk` helper, rescaling each chunk's loss by its share of the step's total token count before `.backward()` so summed gradients across chunks still reproduce DAPO's single globally-normalized loss (same math as the original per-sample rescale, just coarser-grained). `train_micro_batch_size` is set by a dedicated probe (`probe_train_micro_batch_size`, mirroring SFT's `probe_micro_batch_size` pattern) rather than assumed equal to SFT's own probed value (12) -- training-step memory (forward + backward + optimizer state, on top of an already-loaded RL adapter) has a different profile than SFT's teacher-forced batches even on identical hardware, so it's measured on real rollout-shaped synthetic sequences (real prompts, worst-case-length synthetic completions) rather than carried over by assumption.

**Cross-prompt rollout batching (2026-08-07):** the 2026-08-06 fix above still left the actual dominant cost untouched. Reaching `rollout_groups_per_batch=8` kept groups needs ~10-12 attempts/step (observed keep rates 67-80%), and each attempt was a *separate* `sample_group` call -- a separate `model.generate()` for one prompt's `group_size=4` completions (autoregressive, up to 256 tokens, inherently the most expensive part of a step) plus a separate old-logprob forward pass -- never batched across the different prompts sampled within a step. Measured at ~7 min/step before this fix, consistent with paying full NF4-dequant + kernel-launch overhead 10-12 times per step. Replaced `sample_group` with `sample_group_batch(model, tokenizer, rows, ...)`, which takes several *different* prompts at once, left-pads them to a common length for one batched `generate()` call (`repeat_interleave`d by `group_size` so every prompt still gets its own `group_size` completions), strips the left-padding back out immediately after generation (so nothing downstream ever has to reason about left-padded position ids -- avoids a real correctness trap: mixing left-padding from generation with right-padding for a later forward pass in the same tensor would require explicit `position_ids` handling to stay correct, so the fix sidesteps that entirely by returning to a padding-free per-sequence representation before any further batching), then reuses the same right-pad batched old-logprob pattern from the 2026-08-06 fix across all `rollout_prompts_per_batch x group_size` completions at once. `collect_rollout_batch` now samples prompts in chunks of `CFG['rollout_prompts_per_batch']` instead of one at a time; `max_rollout_attempts` keeps its original meaning (a cap on total prompts sampled, not on batches). `rollout_prompts_per_batch` is set by its own probe (`probe_rollout_prompts_per_batch`, sharing the model already loaded for the training-step probe) rather than reusing `train_micro_batch_size`'s probed value -- generation has no backward pass but its KV-cache scales with batch x sequence length, a different memory profile from training that needs its own measurement, run on real prompts through the real `sample_group_batch` code path rather than synthetic data.

**`max_new_tokens_rollout=256` sanity-checked (2026-08-07):** verified directly against the real tokenizer rather than left as an assumed-sufficient default -- gold SQL answer length across 1,500-row samples of `sft_final.jsonl` and both heldout arms tops out at 193 tokens (mean ~75, p99 ~188); not a single gold statement anywhere in the corpus exceeds 256, since every archetype is a single `SELECT`. 256 leaves ~33% headroom above the observed worst case.

**Live sanity log, added after the cross-prompt batching fix (2026-08-07):** `RLTrainer._train_step` now also returns one representative (question, gold, prediction, reward) example per step, printed both to the notebook's live output and `train.log` -- there was previously nowhere to actually read generated SQL text, only aggregate metrics. First real run confirmed the batching fix produces correct generations (reward ~1.0, predicted SQL matching gold exactly), not silently-broken output from the left-padding refactor.

**Batched evaluation generation (2026-08-10):** `evaluate_generation` -- used everywhere a generation-eval metric is reported (RL's periodic per-step eval, the final in-corpus test comparison, and the heldout benchmark section) -- ran one `model.generate()` call per row, completely unbatched. This was tolerable at the original small `eval_gen_sample_size` (60 rows) but became a multi-hour-per-leg bottleneck once the heldout eval sample was raised to cover full arms (~10,088 familiar, ~2,196 unseen rows) -- the same fixed-per-call-overhead problem already fixed for training rollout (2026-08-07), just never applied to the evaluation path. Batched the same way: left-padded multi-prompt `generate()` calls instead of one prompt at a time, decoding each row's completion via `skip_special_tokens=True` from a uniform boundary (no explicit EOS-position search needed here, unlike the rollout fix -- this is eval-only, no downstream old-logprob forward pass that would need the raw un-decoded token ids). Batch size defaults to `rollout_prompts_per_batch x group_size` -- deliberately reusing the concurrency level the rollout batch-size probe already validated as safe, rather than a new guess or a new probe, since greedy eval generation (one sequence per prompt, no `group_size` replication) is strictly lighter per call than what that probe already tested.

**Heldout generation eval scope decision (2026-08-11):** even after both batching fixes above, a real run showed frozen's generation eval alone consuming most of 8 hours at ~70GB/96GB GPU memory, with the SFT-only leg genuinely running (confirmed via the new per-leg "starting" log) but still not finished after several more hours. Root cause isn't a remaining code bug -- it's that batching amortizes per-call *overhead*, not the *sequential depth* of autoregressive decoding (up to `max_new_tokens_eval=256` steps/batch) or KV-cache memory (scales with batch size x sequence length, and these prompts are schema-dominated at ~1,200-1,500 tokens). Generation over the full 12,284-row heldout set x 7 legs (frozen + 3 seeds x {SFT-only, SFT+RL}) was never computationally tractable, batched or not -- this is exactly the cost `eval_gen_sample_size=60` was originally designed to avoid, reintroduced when the heldout sample was raised (the CFG value found to actually be `60000`, not a smaller placeholder, which was also coupled to RL training's periodic eval and the final in-corpus test comparison's `TEST_GEN_SAMPLE`, since they share one key). Decided (2026-08-11): full-coverage generation across every leg isn't worth the wall-clock cost, and the original small-sample design was correct in principle, just sized too small for a final paper claim. Fixed by decoupling and rescoping: `eval_gen_sample_size` reverted to `60` (its original value, no longer shared with heldout); new `CFG['heldout_eval_gen_sample_size']=750` caps only the heldout generation-based metrics (exec-match, exact-match, abstention precision/recall, efficiency speedup) -- ~10x the original sample, still large enough for a defensible paper-level estimate, but tractable. The teacher-forced loss/perplexity/token-acc pass, which needs no generation and is comparatively cheap, still runs over the full heldout arms unconditionally -- full-coverage perplexity is retained, only the expensive generation-based metrics are sampled. Caching interaction noted: since frozen's result had already been computed and cached under the old full-coverage setting before this fix, it had to be manually deleted so it would be recomputed on the same sample as the SFT/RL legs -- otherwise the 3-way comparison would silently mix a full-coverage frozen baseline with sampled SFT/RL legs.

**Second unbatched hot path + missing progress visibility (2026-08-11):** the 2026-08-10 fix only touched generation (`evaluate_generation`/`_greedy_preds`); `make_loader` (used for the teacher-forced loss/perplexity/token-acc pass) had a separately hardcoded `batch_size=1`, inherited from SFT's original pattern and never revisited even after SFT's own probe found much larger batches safe. With the heldout eval sample raised to cover full arms, this ran one-sample-at-a-time over 10,088 (familiar) + 2,196 (unseen) rows for every one of 7 legs (frozen + 3 seeds x {SFT-only, SFT+RL}) -- likely the dominant remaining cost even after the generation fix, since `collate_fn` already implements correct padding/attention-mask/label-masking for any batch size and needed no other changes to support batching. Now parameterized (`cfg.get('eval_loader_batch_size', cfg.get('train_micro_batch_size', 1))`), reusing the already-probed-safe training batch size as a conservative default for a forward-only pass that could likely go higher. Separately, the heldout driver cell printed a result only after the frozen leg -- nothing after any of the subsequent 6 legs, so a working-but-slow run and a stalled one were indistinguishable from the notebook's output alone. Added a start/done print (with elapsed minutes) and a full-results print around each seed's SFT-only and SFT+RL legs, matching the visibility the frozen leg already had.

**Batched `_greedy_preds` (2026-08-10):** the SFT-vs-RL head-to-head efficiency cell (compares each model's own SQL against the other's, not against gold -- added directly against real results, judging by its reference to an observed ~0.982 exact-match rate) had the same one-row-at-a-time `model.generate()` pattern as `evaluate_generation` before its batching fix, in a separate loop. Batched identically (multi-prompt `generate()` calls, same `rollout_prompts_per_batch x group_size` default), leaving the rest of the cell's logic (exact-match exclusion, cache-fair pairwise timing, median-of-medians) untouched.

**Early stopping (2026-08-09):** seed 43 reached its best exec-match at step 20 and never improved afterward, for however many further steps it ran -- the same plateau-past-a-point pattern already observed in SFT (seed 42's 3rd epoch, cut for seeds 43/44). Added `CFG['early_stopping_patience']=5` (in eval-checks, i.e. multiples of `eval_every_n_steps`, not raw steps) to `RLTrainer.train()`: a counter increments on every eval check that doesn't beat `best_score` and resets to 0 on one that does, and the loop breaks once the counter reaches the patience value. The counter is checkpointed in `training_state.pt` (defaults to 0 for older checkpoints predating this fix) so a resume continues counting rather than restarting the patience window. `seed_is_done()` in the multi-seed driver was also updated -- it previously only recognized a seed as finished if `history.json` reached the full `num_rollout_steps`, which early stopping means may never happen; it now also checks the persisted `checks_since_improvement` against the patience threshold, otherwise an early-stopped seed would be wrongly reloaded and immediately re-trigger early stopping on the next run.

**Inter-seed GPU memory cleanup (2026-08-09):** seed 43 hit an OOM even at the batch-size probe's *second*-best `train_micro_batch_size` (deliberately not using the probe's top pick, as a safety margin). The probe measures on a clean, freshly-loaded model early in the notebook; by the time a later seed starts, whatever memory `del trainer` didn't immediately release (Python's refcounting doesn't guarantee instant collection of objects with internal cross-references, e.g. an optimizer holding per-parameter state) can still be occupying the CUDA allocator's cache, on top of ordinary fragmentation from `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`'s mitigation not being a complete fix. Added an explicit `gc.collect()` before `torch.cuda.empty_cache()` (plus a `torch.cuda.synchronize()` to ensure no kernels are still in flight when memory stats are read) at both places a model gets discarded -- the batch-size-probe cleanup and the multi-seed driver's per-seed cleanup -- rather than relying on `del` and `empty_cache()` alone.

**Full-coverage rollout sampling (2026-08-08):** `collect_rollout_batch` originally drew prompts via `random.choice(prompt_pool)` -- with replacement, so coverage of the train pool over a fixed step budget was probabilistic and incomplete: measured directly, only ~15% of the ~9,956-row pool was ever sampled even once over 200 steps, ~73% over 1200 (a with-replacement draw count exceeding the pool size still leaves a meaningful fraction untouched, by the same math as the birthday paradox). Replaced with `CyclicPromptSampler`: shuffles the full pool once, draws without replacement until exhausted, then reshuffles into a fresh cycle -- guarantees every training instance is sampled at least once per `len(prompt_pool)` draws, deterministically rather than probabilistically. Sampler state (shuffle order, position, cycle count) is checkpointed alongside everything else in `training_state.pt` so a resume continues the same cycle instead of restarting it (falls back gracefully to a fresh cycle if resuming from an older checkpoint that predates this fix). A `[sampler] cycle N starting` log line marks each full pass through the pool, giving a direct, visible coverage milestone instead of an unverifiable assumption.

**Checkpoint-loss incident and fix (2026-08-07):** a real run lost ~158 steps of progress on a Colab disconnect -- `training_state.pt` resumed from step 1 despite ~160 steps having actually run, even though `_save()` was already being called every single step. Root cause is almost certainly Google Drive's FUSE mount not being synchronously durable: each checkpoint is large (~850MB -- adapter weights + full AdamW optimizer state for 71M trainable params), and Drive's background uploader can fall behind every-step writes; a hard disconnect then loses whatever hadn't finished syncing, even though the Python-level save "succeeded" (no exception, no `[warn]` logged). The cross-prompt batching fix makes this worse, not better, since faster steps mean less real wall-clock time for Drive to catch up between writes. Fixed by adding `CFG['save_every_n_steps']=5` (checkpoint every 5 steps instead of every step, plus always on a new best and on the final step) -- reduces write volume ~5x and bounds the redo cost on a future disconnect to at most 4 steps instead of an unbounded amount. Separately, found and fixed a genuine crash-atomicity gap in `_atomic_save_adapter` (inherited from SFT's checkpointing code, unrelated to the Drive-sync issue): it did `shutil.rmtree(path)` (delete the old checkpoint) *then* `os.replace(tmp, path)` (install the new one) as two separate operations, so a crash landing between them left `path` missing entirely, not even the old version. Fixed by demoting the current checkpoint to `path + '.prev'` (a fast metadata-only rename, not a copy) before promoting the new one, and only dropping `.prev` after the promotion succeeds -- narrows the crash window from "however long the old rmtree + new write took" to a couple of fast renames, and `RLTrainer._build_model_and_tokenizer` now falls back to `.prev` if `last/` is ever found missing on resume.

**Global token-level normalization under per-sample gradient accumulation:** DAPO's loss normalizes by the total response-token count of whatever batch it's given. Padding an entire rollout batch (which mixes very different completion lengths) into one tensor for a single forward pass would undercut the memory-conservative per-sample approach above, so each sample instead gets its own forward pass, and its returned loss is rescaled by `(that sample's token count) / (total token count across the whole kept batch)` before `.backward()`. Because `.backward()` accumulates gradients additively across calls, the sum of these rescaled per-sample backward passes reproduces the gradient of the single globally-normalized loss DAPO specifies, without ever materializing a padded batch tensor.

**Checkpoint linkage to SFT:** each RL run loads a specific seed's SFT `best/` adapter directly (`PeftModel.from_pretrained` on the same 4-bit base model SFT used) as its starting point -- RL continues the exact adapter weights SFT produced, rather than training a fresh adapter with a reward signal alone. Learning rate is set an order of magnitude below SFT's (`1e-5` vs `2e-4`), since RL updates should perturb an already-converged, competent policy gently rather than risk destroying SFT-learned SQL-generation competence while shaping behavior toward reward.

**Best-checkpoint selection during RL** uses the periodic execution-match rate on the same fixed `dev` subsample SFT used, not the DAPO loss value -- policy-gradient loss is not a reliable proxy for output quality (it can decrease while the policy degrades, or fluctuate independent of task performance), so checkpoint selection uses the actual verifiable task metric instead, consistent with standard practice in RLHF/RLVR pipelines.

**Final comparison** reuses each seed's already-computed `sft_outputs/seed_<seed>/test_eval.json` as the baseline (no need to recompute -- SFT already produced it) and evaluates the RL `best/` checkpoint on the identical held-out `test` split and fixed generation-eval subsample, mirroring exactly how SFT compared itself against the frozen base model. Extended to a three-way table joining `sft_outputs/test_baseline.json` (frozen base), each seed's SFT `test_eval.json`, and RL's own result -- the frozen-base-vs-SFT-only-vs-SFT+RL ablation. Note that `sft_train.ipynb` is not being further edited once SFT training is actively running, so the frozen/SFT-only rows of this table predate the efficiency metric below and show `nan` for it -- only the SFT+RL row has a real measured value.

**Standalone efficiency metric** (`gen_efficiency_speedup`, distinct from the training reward): median (gold execution time / predicted execution time) among test-set rows scored exec-correct, measured the identical cache-fair way as the reward (untimed warm-up pass on both queries, then a timed second execution of each with randomized order) so the reported metric and the training signal it's meant to explain share one methodology rather than two that could disagree for unrelated reasons. `nan` if no row in the sample was correct, since efficiency isn't meaningful to measure over wrong answers. Added to `evaluate_generation`, so it's automatically included wherever that function's output flows -- `evaluate_checkpoint_on_test`'s final test-split report, in particular.

**Ablation infrastructure:** `CFG['run_name']` namespaces `rl_outputs/` (`rl_outputs/<run_name>/seed_<seed>/...`) so more than one RL configuration can be trained and evaluated without overwriting a prior run's checkpoints and logs. Exists specifically to support the correctness-only vs. correctness+efficiency ablation: rerun with `CFG['efficiency_bonus_max'] = 0` under a different `run_name`, and compare that run's per-seed test results against the default (`efficiency_bonus_max > 0`) run's -- both produce real, identically-measured `gen_efficiency_speedup` values, so the comparison is apples-to-apples. Not yet run as of this writing -- the infrastructure exists, the second training pass (and the correctness-vs-efficiency and generalization-beyond-training-distribution evidence it would provide) does not yet.
